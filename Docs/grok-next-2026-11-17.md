### 2. The hit reaction warning on creatures (a real cooked-build bug)

Every hit on a creature that plays a single looping clip logs:
`Setting an additive animation (NPC_MM_HitReact_Front_Lgt_01) on an AnimSingleNodeInstance ... is not allowed. This
will not function correctly in cooked builds!` The Gatekeeper and the Dead Air creatures do it.

- **Where:** `ADCCCharacterBase::Multicast_PlayHitReaction_Implementation` and `PlayOneShotAnimation` in
  `Characters/DCCCharacterBase.cpp`. `PlayOneShotAnimation` already checks `GetAnimationMode()`.
- **What:** when the mesh is in `EAnimationMode::AnimationSingleNode` and the clip is additive
  (`UAnimSequence::IsValidAdditive()`), skip the clip. Keep the rest of the hit reaction: the 0.08 s defender pause
  (`HitStutterSeconds`, `CustomTimeDilation`) must still happen, because that is the part Zoe asked for.
- **Check:** `python Tools/run_test.py DCCGateGameMode "DCC.GateIn 99 6, DCC.Fight 40 9" 12 3 12 hitreact`, then
  `grep -c "is not allowed" Saved/Logs/hitreact.log` must be 0, and the log must still show hits landing.
- **Done when:** zero warnings, hits still land, logged.

### 5. The belt from a client, not just the host (most important before the next session with friends)

Every belt test so far ran as the host. Zoe plays with friends who join her, so a joined player's belt has to work:
the lamp (`UDCCWalletComponent::Server_SetMineLamp`), lightsticks (`Server_ThrowLightstick`), the body cam
(`ToggleRecording`), tools and food (`ADCCCharacterBase::Server_UseBeltItem`) all go through server calls.

- **How:** two game windows on this PC. First a host:
  `UnrealEditor.exe <uproject> "/Engine/Maps/Entry?game=/Script/DungeonCrawlerDenver.DCCHauntGameMode?listen" -game -windowed -ResX=960 -ResY=540 -log=host.log`
  then a client: `UnrealEditor.exe <uproject> 127.0.0.1 -game -windowed -ResX=960 -ResY=540 -log=client.log -ExecCmds="..."`
  (engine path and uproject as in `Tools/run_test.py`). Start each with `subprocess.Popen` and keep both process
  ids; close only those two. `Tools/editor_ctl.py shot` captures every Unreal window, so one call gets both.
  Dev commands act on the local crawler of the window they run in, so put the belt commands in the **client's**
  `-ExecCmds`.
- **Check from the client:** `DCC.Belt 1` (body cam: the REC light shows over the client crawler on the **host's**
  screen), `DCC.Belt 2` (lamp off: the host's screen shows that crawler's lamp out), `DCC.Belt 3` then `DCC.Click`
  (a lightstick appears on both screens; the count drops on the client's belt). Then the same in Fourteener with
  `DCC.Outfit` and the food slot (`DCC.NextFood`, `DCC.Belt 4`).
- **Watch for:** the client's player name in `client.log`. If it also comes up as "Zoe", say so: two copies on one
  PC may share her profile.
- **Time box:** if the two windows will not connect within about 30 minutes of trying, stop, write exactly what
  happened (the log lines around the join), and move on.
- **Done when:** each belt action is confirmed from the client on both screens, or the failure is written down
  precisely. A real multiplayer bug found here is worth more than anything else on this list; fix it only if it is
  small and clear, and describe it either way.
